## 修复②：ProcurementTask 缺列导致 findMany 报错
- **现象**：`procurementTask.findMany()` 报 `The column main.ProcurementTask.procurementCategory does not exist in the current database.`（service.ts:290）。
- **根因**：上次把 `procurementCategory/techQuality/acceptanceMethod/paymentMethod` 加进了 schema 并 `generate`，但**没对 SQLite 跑 `db push`**，dev.db 的表结构从未加这几列（仅 14 列）。
- **修复**：停后端（35432+supervisor 32444）→ `prisma db push --schema prisma/schema.sqlite.prisma`（567ms，DB 已与 schema 同步，并自动重新 generate 了 sqlite client）→ 重启（PID 35892）。
- **验证**：PRAGMA 确认 ProcurementTask 现 18 列（含 4 新列）；独立脚本 `findMany({select:{procurementCategory...}})` 返回 2 行，无缺列错。
- **经验**：改 schema 后务必 `db push`（不只是 `generate`），否则 DB 表结构与 client 不一致会报缺列。双 schema 流程固定为 `gen-sqlite-schema → db push(--schema sqlite) → generate`。

## 修复③：采购模块详情加载失败（"任务详情加载失败，请关闭后重试"）
- **现象**：成交报告导入「响应单位情况汇总表」后，编辑弹窗告警"任务详情加载失败，请关闭后重试"；首次打开（无记录）正常，导入后（有记录）即报错。
- **根因（前端系统性 bug）**：后端统一响应包装 `{code,data}`，前端 `http` 拦截器对 `code===0` 已 `return body.data`，故 `res` 已是完整 payload（含 `task` 与 `data` 记录两字段）。
  但各模块 `loadDetail` 旧逻辑 `const d = res?.data ?? res` 把 payload **自身的 `data` 字段**（模块记录）误当成 axios 包装层，
  导致记录存在时 `d` 变成缺 `task` 的纯记录 → `currentTask = null` → 触发告警。首次加载 `data:null` 走回退才正常，导入后记录存在即炸。
  同样的原因还会导致"重开已有记录时表单被清空"。
- **影响范围**：六个采购模块页面全部中招（ResultReport / Notice / Document / FrameworkExplanation / PreMeetingMinutes / PriceCompare）。
- **修复**：六处 `const d = res?.data ?? res` → `const d = res`（已加注释说明拦截器已解开 body.data）。`Initiate.tsx` 的 `detail` 是 task 序列化对象、无 `data` 字段，不受影响，未改。
- **验收**：`tsc --noEmit` 通过；`vite build` 通过；以真实 payload 形态做逻辑验证——旧逻辑 `d.task=undefined`（告警），新逻辑 `d.task` 正常且 `d.data.unitCount` 可取（表单正常）。
- **提交**：`be7b85b`（9 文件，含 `.workbuddy/memory/` 按新规则一并上传），`3b02e81..be7b85b main -> main` 已推送。
