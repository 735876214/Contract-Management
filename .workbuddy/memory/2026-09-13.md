## NAS 部署报错诊断与修复（pull access denied / context not found）
- 用户首次 `docker compose up`（漏 --build，且只拷了 compose+.env）报错：`pull access denied for cms-backend/cms-frontend`、`unable to prepare context: …/CMS/server not found`。
- 根因：compose 同时有 `build:`+`image:`，无 --build 时优先去 Docker Hub 拉 `cms-backend:latest`（公有不存在）→ 拒绝；且 server/ web/ 源码没随 compose 拷到 NAS，build context 缺失无法本地构建。
- 修复：`docker-compose.yml` 去掉两处 `image:` 行，强制走本地 build（即使忘记 --build 也会自动构建，不再去拉私有镜像）。已提交 `dae27ea`。
- **复发+根治**：用户 NAS 上跑的是删 image 行之前的旧 compose，仍报 `pull access denied for cms-backend/cms-frontend` + `COMPOSE_BAKE=true` 提示。根因=NAS 那份 compose 带 `image: cms-*:latest`，提交 `dae27ea` 后未同步到 NAS。
  - 澄清：**GitHub 只有源码没有 Docker 镜像**，不存在「从 GitHub 拉 cms-backend 镜像」这回事；正确姿势是 `git pull` 源码 + 本地 build。
  - 根治：compose 两服务再加 `pull_policy: build`（提交 `b6f5901`），双保险——即使误加 image: 也优先本地构建而非拉取。NAS 侧若非 git 仓库，可用 `sed -i '/^    image: cms-/d' docker-compose.yml` 删旧行后 `docker compose up -d --build`。
- **正确部署姿势（关键）**：必须把整个 `server/`（Dockerfile/package.json/src/prisma 等）与 `web/`（Dockerfile/package.json/vite.config.ts/src/nginx.conf 等）连同 `docker-compose.yml`、`.env` 放到 NAS 同一目录，再 `docker compose up -d --build`。`COMPOSE_BAKE=true` 仅为性能提示，与报错无关。
- 经验：NAS 自托管构建必须随 compose 分发源码构建上下文；只拷 compose 会因无法 pull 私有镜像而失败。

  - 数据卷 `volumes: - /volume1/docker/cms/data:/data` —— 群晖路径已内联；其他 NAS 改此行即可，或 .env 设 CMS_DATA 覆盖。
  - 头部部署步骤改为「.env 可选，不准备也能直接跑」。
- **配套防坑**：`.env.example` 的 JWT_SECRET/CMS_DATA 改为注释态，避免 `cp .env.example .env` 后占位串 `change-me...` 顶掉内联默认值（${VAR:-默认} 仅在未设/空时生效，设了非空占位会顶掉）。`scripts/nas-deploy.sh` 同步改为 .env 缺失时复制示例且**不强制退出**（内联默认值可直接跑）。
- 安全提示：内联默认密钥会进仓库（私有仓可接受）；想更稳就在 .env 用 `openssl rand -base64 48` 覆盖。
