## 修复②：ProcurementTask 缺列导致 findMany 报错
- **现象**：`procurementTask.findMany()` 报 `The column main.ProcurementTask.procurementCategory does not exist in the current database.`（service.ts:290）。
- **根因**：上次把 `procurementCategory/techQuality/acceptanceMethod/paymentMethod` 加进了 schema 并 `generate`，但**没对 SQLite 跑 `db push`**，dev.db 的表结构从未加这几列（仅 14 列）。
- **修复**：停后端（35432+supervisor 32444）→ `prisma db push --schema prisma/schema.sqlite.prisma`（567ms，DB 已与 schema 同步，并自动重新 generate 了 sqlite client）→ 重启（PID 35892）。
- **验证**：PRAGMA 确认 ProcurementTask 现 18 列（含 4 新列）；独立脚本 `findMany({select:{procurementCategory...}})` 返回 2 行，无缺列错。
- **经验**：改 schema 后务必 `db push`（不只是 `generate`），否则 DB 表结构与 client 不一致会报缺列。双 schema 流程固定为 `gen-sqlite-schema → db push(--schema sqlite) → generate`。

## 修复①：Prisma datasource 协议不匹配导致后端全请求报错
- **现象**：后端任意走 JWT 的请求报 `Invalid this.prisma.user.findUnique() … Error validating datasource db: the URL must start with postgresql://`（jwt.strategy.ts:22）。
- **根因**：上次构建验证时双 schema 各 generate 一次，且 `schema.prisma`（postgresql）最后执行，覆盖了 `node_modules/.prisma/client`，
  使运行时 client 按 postgresql 校验 `DATABASE_URL="file:./dev.db"`（SQLite）→ 校验失败。
- **修复**：
  1. 杀掉后端进程树（app 5676 + `nest start --watch` 监督 9400/34124/35732），释放 SQLite 引擎锁，端口 3000 释放。
  2. `prisma generate --schema prisma/schema.sqlite.prisma`（最后执行，生成 SQLite client，inlineSchema provider=sqlite）。
  3. 清理上次失败 generate 残留的 `query_engine*.tmp*` 临时文件。
  4. `nest start --watch` 重启后端（PID 35432），日志 `Nest application successfully started`，:3000 监听正常。
  5. 独立脚本复跑 `prisma.user.findUnique()` → `OK query executed, result: null`，确认 postgresql 协议错消失。
- **经验写入**：`MEMORY.md`「本地开发数据源」补 ⚠️ 致命坑——默认 `prisma:generate` 落 postgres，必须保证 `schema.sqlite.prisma` 的 generate 最后执行。
- 清理临时文件：`node_procs.txt`、`server/dev.db`（验证脚本误建的空库，已删；真实库 `server/prisma/dev.db` 完好）。
