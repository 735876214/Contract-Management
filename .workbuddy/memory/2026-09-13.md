## NAS 部署报错诊断与修复（pull access denied / context not found）
- 用户首次 `docker compose up`（漏 --build，且只拷了 compose+.env）报错：`pull access denied for cms-backend/cms-frontend`、`unable to prepare context: …/CMS/server not found`。
- 根因：compose 同时有 `build:`+`image:`，无 --build 时优先去 Docker Hub 拉 `cms-backend:latest`（公有不存在）→ 拒绝；且 server/ web/ 源码没随 compose 拷到 NAS，build context 缺失无法本地构建。
- 修复：`docker-compose.yml` 去掉两处 `image:` 行，强制走本地 build（即使忘记 --build 也会自动构建，不再去拉私有镜像）。已提交 `dae27ea`。
- **复发+根治**：用户 NAS 上跑的是删 image 行之前的旧 compose，仍报 `pull access denied for cms-backend/cms-frontend` + `COMPOSE_BAKE=true` 提示。根因=NAS 那份 compose 带 `image: cms-*:latest`，提交 `dae27ea` 后未同步到 NAS。
  - 澄清：**GitHub 只有源码没有 Docker 镜像**，不存在「从 GitHub 拉 cms-backend 镜像」这回事；正确姿势是 `git pull` 源码 + 本地 build。
  - 根治：compose 两服务再加 `pull_policy: build`（提交 `b6f5901`），双保险——即使误加 image: 也优先本地构建而非拉取。NAS 侧若非 git 仓库，可用 `sed -i '/^    image: cms-/d' docker-compose.yml` 删旧行后 `docker compose up -d --build`。
- **正确部署姿势（关键）**：必须把整个 `server/`（Dockerfile/package.json/src/prisma 等）与 `web/`（Dockerfile/package.json/vite.config.ts/src/nginx.conf 等）连同 `docker-compose.yml`、`.env` 放到 NAS 同一目录，再 `docker compose up -d --build`。`COMPOSE_BAKE=true` 仅为性能提示，与报错无关。
- 经验：NAS 自托管构建必须随 compose 分发源码构建上下文；只拷 compose 会因无法 pull 私有镜像而失败。

## NAS 部署最终定案：改用 git 克隆构建上下文（放弃 ghcr）
- **背景/根因**：ghcr 私有镜像方案在 NAS 上持续 `Head "https://ghcr.io/.../manifests/latest": denied`。用户提供的 PAT 经 API 验证**权限范围仅 `repo`**（无 `read:packages`/`write:packages`），故：①无法用 API 把包设为 Public（需 write:packages）；②不能作为 ghcr 登录凭据拉私有包（需 read:packages）。而 `repo` 权限正好能克隆私有仓库源码。
- **决策**：放弃 ghcr 预构建镜像路线，改回「构建时由 Docker 直接从 GitHub 私有仓库克隆源码」，彻底不依赖 ghcr、也无需在 NAS 放源码。
- **落实**（提交链待补）：
  - `docker-compose.yml`：两服务删掉 `image:`/`pull_policy`，改为 `build.context: "https://x-access-token:${GITHUB_TOKEN}@github.com/735876214/Contract-Management.git#main:server"`（前端 `#main:web`），`dockerfile: Dockerfile`。`#main:subdir` 是官方确认的「分支+子目录」git 上下文片段语法；URL 内嵌 token 由 git 原生支持。
  - `.env.example`：新增必填 `GITHUB_TOKEN=`（repo 权限 PAT）；JWT_SECRET/CMS_DATA 仍为可选覆盖（compose 内联默认值）；注明仓库若设为 Public 可留空并删 context 里的 `x-access-token:` 部分。
  - `scripts/nas-deploy.sh`：重写为「校验 .env 含非空 GITHUB_TOKEN → `docker compose up -d --build`」，删掉 ghcr pull / local build 分支；每次重建都重新克隆 main，天然「每次从 GitHub 拉最新代码」。
- **Dockerfile 兼容性已核对**：`server/Dockerfile`/`web/Dockerfile` 均为子目录相对写法（WORKDIR /app/server、COPY . .、nginx.conf 在 web 子目录），与 `#main:server`/`#main:web` 子目录上下文完全兼容；`.dockerignore` 在各自子目录内会被 git 上下文应用。
- **NAS 侧操作**：`.env` 必须填 GITHUB_TOKEN；Container Manager UI 直接 `docker compose up --build` 即可（git 克隆在构建时自动发生，无需 SSH 拷源码）。`.github/workflows/build.yml`（ghcr 构建推送）现已无用，可保留或删除。
- **安全**：用户把真实 PAT 明文贴入对话，已提醒部署完成后吊销/重置该 token。

## NAS 后端崩溃坑：Prisma schema 引擎缺 OpenSSL（2026-09-13 晚）
- **现象**：`docker compose up` 后 `cms-frontend` 能起、能访问登录页，但 `cms-backend` 反复重启；日志报 `Error: Schema engine error ... Please manually install OpenSSL`；前端登录 `502 / upstream Host is unreachable`（backend 容器崩了）。
- **根因**：`server/Dockerfile` 基础镜像 `node:20-slim`（Debian bookworm）默认**没装 openssl**；Prisma 5.10 的 schema 引擎二进制依赖 OpenSSL 共享库（libssl3），`prisma db push`（`CMD` 启动第一步）直接崩。
- **修复**（提交 `c066a3b`）：在 `server/Dockerfile` 的 **build 与 runtime 两阶段** 均加 `RUN apt-get update && apt-get install -y --no-install-recommends openssl ca-certificates && rm -rf /var/lib/apt/lists/*`。
- **触发重推**：改 Dockerfile 后需等 GitHub Actions（build.yml）重建推送 `cms-backend:latest` 完成，NAS 再 `up -d --pull always`（或 `docker compose pull`）才会拿到带 openssl 的新镜像。光改 compose 不够。
- **端口补充**：前端对外端口由 `8080` 改为可配置 `${CMS_HTTP_PORT:-9080}:80`（8080 在 NAS 也被占）；用户侧可在 `.env` 设 `CMS_HTTP_PORT=9221` 等，或反代指向对应端口。

## GitHub Actions 构建过慢优化（2026-09-13 晚）
- **现象**：每次 push 后 Actions「Build and Push CMS Images」跑 20~40 分钟，太久。
- **根因**：① backend/frontend 各构建 `linux/amd64,linux/arm64` 双架构，arm64 在 x86 runner 上靠 QEMU 软模拟，nest build/vite build 等 CPU 密集任务降速数倍~十倍（最大头）；② 无 buildx 层缓存（无 `cache-from/to: type=gha`），每次冷构建重新 npm install+编译；③ 两步串行。
- **优化**（提交 `e1e6ed7`）：仅 `linux/amd64`（NAS 为 x86_64，砍掉最慢的 QEMU 段）；backend/frontend 用 matrix 并行 job（时间取最大）；加 `cache-from/to: type=gha,mode=max`。构建时间可缩短一半以上，增量更快。
- **备注**：若将来确有 ARM NAS，把 matrix 各项 `platforms` 改回 `linux/amd64,linux/arm64` 即可（会重新变慢）。
