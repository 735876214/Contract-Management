## 统一计算引擎可行性调研（只读，未改代码）
- 用户反映各模块频繁出现计算错误、同月不同合同/材料结果不一致，评估抽离统一计算引擎。结论：可行但须先统一口径，而非单纯搬公式。
- 根因（三路 Explore 并行调研汇总）：
  1. 含税价/合价公式前后端重复 8+ 处，round2/round4/toFixed(2) 混用；前端 `ContractItemTab.tsx` 的 round4 无 EPSILON，后端 `money.ts` 带 EPSILON。
  2. 税率单位双轨：Contract.taxRate/Invoice.taxRate 小数（0.13），ContractMaterial.taxRatePct/ReceiptOrderDetail.taxRate 百分数（13）；导入用 `>1 ? /100` 启发式。
  3. 月度 key 多源且分组不统一：结算 `contractId|YYYY-MM`、合同台账 合同+年、Dashboard 仅月、Excel SUBTOTAL(109)；月份字符串排序有 `"2026-10" < "2026-2"` 错序。
  4. 日报导出 `2026年8月` 再导入 `Number(...)` → NaN 丢账期；`toISOString().slice(0,10)` UTC 取日在 UTC+8 可跨月。
  5. 逾期利息双实现：`overdue-calculator.recalculate` vs `finance.service.listOverdue`，期初累计/上限/asOfDate 口径不同。
  6. ProcurementTotalItem 金额用 Float；SQLite schema 生成时剥离 Decimal 精度，本地与生产行为不同；采购阶段金额存 JSON 由前端算。
- 建议方案：`shared/calc` 前后端同构纯函数分四层——L0 输入归一化（Decimal/税率/月份/日期）、L1 计算原语（round、含税价、合价、比率）、L2 业务规则（月度聚合器、逾期利息单一引擎）、L3 输出契约（落库/预览/Excel 同一结果 + golden case）。
- 落地顺序：先 golden case 固化口径 → 抽共享原语替换内联计算 → 合并月度聚合与逾期利息实现 → 数据层整改（Float→Decimal、税率单轨、Excel 合计改服务端值）。
