# 手机端可行性评估（375px 实测核查）

> 核查方式：Edge headless + CDP，按仓库 `docs/development.md §5.2` 流程，在 **375×812 / dpr2** 视口下逐路由渲染实测。
> 覆盖 **48 条真实路由**（`web/src/router.tsx` 全量），注入管理员 token 与默认项目，等骨架渲染完成后采集：
> 视口横向溢出、实测横向溢出元素、表格横向隐藏宽度（横滑屏数）、冻结列、触控目标尺寸、弹窗表单布局。
> 只读核查，未改动任何仓库代码。核查日期 2026-10-24。

## 0. 结论

**可行，且成本远低于通常预期**——但正确方向是「让现有 SPA 达到手机可用 + PWA 轻量化」，不是「做手机 App」。

| 判定项 | 结论 | 依据（实测/代码） |
|---|---|---|
| 技术栈是否支持 | ✅ 完全支持 | React18+AntD5 本身响应式；`DESIGN.md §10` 已定双层响应式模型与「≥375 可读可操作」验收目标 |
| 骨架是否响应式 | ✅ 已就位 | 375 下侧栏抽屉实测 375×812、19 个菜单项、可竖向滚动；顶栏精简、面包屑正常 |
| 是否要重写 | ❌ 不需要 | 48 页**仅 2 页**出现横向溢出（`/labor/auth` +26px、`/system/dict` +48px） |
| 表单录入是否可用 | ✅ 可用 | 375 下弹窗实测 359px 宽、标签竖排单列、控件高 40px、底部按钮 40px |
| 主要短板 | ⚠️ 集中在**宽表格**与**行内小按钮** | 合同台账 41 列需横滑 **16.8 屏**；基础库行内操作按钮 44×30px |
| 做成原生 App | ❌ 不建议 | 无收益、成本 3–5 人月，且 48 页业务表单需全部重做 |

预估：**把手机端做到"真能用"，10–20 人日**（收尾 1–2、表格移动化 5–8、PWA+现场能力 5–10）。

## 1. 已经就位的基建（不要重做）

- **规范层**：`DESIGN.md §10` 双层模型——外壳按视口（`useResponsive()`），组件按容器（`.cq` + `@container`、`useContainerWidth()`）；四条硬性约定含「表格必须声明 `scroll={{ x }}`、操作列 `fixed:'right'`」「弹窗宽度全局 `max-width: calc(100vw - 16px)` 兜底」。
- **代码覆盖率实测**：`scroll={{ x }}` 59 处、`fixed: 'left'|'right'` 57 处（49 个页面文件）。
- **外壳**：375 下 `AppSider` 自动降级 Drawer，实测抽屉宽 375、菜单 19 项、`overflow-y:auto`。
- **弹窗/抽屉即容器**：`containers.css` 统一给 `.ant-modal-body/.ant-drawer-body` 标记容器，故弹窗内表单自动单列——实测「新增字典类型」弹窗 `labelColumns=1`、`minCtrlH=40`。
- **列表页筛选区**：容器驱动列数（容器宽 ÷240px，下限 2），375 下 2 列、输入框高 40px。

这些正是「手机端 70% 基建已完成」的来源：剩下 30% 是**表格表达**与**触控尺度**，不是架构问题。

## 3. 短板清单（按优先级）

### P0-1 宽表格在手机上不可用（核心痛点）

- `/contract/list` 41 列、横滑 **16.8 屏**；`/daily/report` 43 列、**16.9 屏**；`/daily/asset` 29 列、10.5 屏。
- 且这 3 页**无 `fixed:'right'` 操作列**（实测 `fixR=0`），`/base/project`、`/base/material`、`/base/template`、`/base/clause`、`/system/user`、`/system/dict`、`/system/log`、`/procurement/initiate`、`/message` 同样未冻结操作列 → **改一行数据要先横滑 3–17 屏**。
- 表格横向滚动本身是通的（`overflow-x:auto` 全部生效，`/system/ai-register` 除外无溢出），所以这是**表达问题而非功能问题**。

### P0-2 两处真实破版

1. `/labor/auth` +26px：卡片头 `ant-card-extra` 内「刷新 / 新增 / 授权委托书 / 导出 Excel」横排按钮组宽 372px > 375 可视区（实测最右「导出 Excel」按钮溢出 26px）。
2. `/system/dict` +48px：卡片头 4 个按钮组溢出 48px **且**该页是主从两栏布局，右侧明细栏被挤出视口——手机上该页基本只能看左栏。

### P1-1 行内操作按钮触控目标偏小

- 实测基础库/系统页行内按钮为 **44×30px**（`编辑/停用/删除` 并排），高 30px < 44px 建议值，误触风险高且是三连击（删除就在旁边）。
- 触控 <40px 占比：`/base/clause` 67%、`/system/dict` 61%、`/system/user` 60%、`/base/template` 55%、`/base/material` 52%、`/base/project` 50%、`/base/supplier` 47%、`/system/log` 44%。
- 反面参照：`/dashboard`、`/daily/*`、`/statistics`、`/ai/*` 已达 0–25%，说明规范本身是对的，只是行内按钮没有专门尺度。

### P1-2 多页签条在手机上无意义

37px 高、需横滑 0.6k px 才能关闭，且与抽屉导航功能重复。

### P2-1 交付形态缺 PWA / 离线 / HTTPS

无 manifest 与 SW → 无安装到桌面、无离线壳、弱网（工地现场）体验差；若走公网还需 HTTPS（当前 JWT 存 `localStorage`，无 HTTPS 时既有安全面又有 `getUserMedia` 不可用的问题）。

### P2-2 现场能力缺口（非技术债，是产品机会）

收领单、日报、资产台账的现场场景天然需要**拍照/相册上传**与**扫码**，目前只能靠文件选择器。

## 4. 推荐路线（三阶段）

**阶段 A · 收尾止血（1–2 人日）**
1. 修 `/labor/auth`、`/system/dict` 卡片头按钮组：`≤md` 时改为「主按钮 + 更多下拉」。
2. `/system/dict` 主从两栏：`≤md` 改为「列表 → 点进详情」单栏切换。
3. 多页签条 `≤md` 默认折叠为单页签 + 下拉（`TagsView` 已有 `is-compact` 变体可复用）。
4. 行内操作按钮 `≤md` 提到 40×40，删除类改二次确认气泡。

**阶段 B · 表格移动化（5–8 人日，主要工作量）**
1. **移动端列模板**：复用已有「列设置」能力，为 10 个高频台账预置移动默认列集（4–6 列：编号/名称/金额/状态/日期），桌面列不变。这一步就能把 16.8 屏降到 2–3 屏，收益最大、改动最小。
2. **补齐 `fixed:'right'`**：把缺失的 9 页操作列补齐（规范 §10.1 第 2 条本来就这么要求）。
3. **卡片化**：只对 3 个最高频页（`/daily/receipt`、`/settlement/order`、`/contract/list`）做 `≤md` 的行卡片视图，其余页走列模板即可。

**阶段 C · PWA 与现场能力（5–10 人日）**
1. `manifest.webmanifest` + 图标 + `apple-mobile-web-app`，实现"添加到主屏幕"全屏运行。
2. 最小 Service Worker：应用壳与静态资源缓存（离线壳，不含业务数据离线写，避免与 PostgreSQL 唯一事实源冲突）。
3. HTTPS 部署（NAS 反代 + 证书），顺带解锁相机。
4. 收领单/日报加「拍照上传」（`accept="image/*" capture` 即可，无需 App）。

**不做**：原生 App / React Native 重写（48 个业务页 + 65 处 Modal 全部重做，3–5 人月，收益仅是相机与推送）；独立移动端 SPA（双端维护成本大于收益）。

## 5. 验收建议（补进仓库规范）

1. 真机冒烟：现有验收只有 Chromium 模拟，至少补 iOS Safari + Android Chrome 各一台过一遍 P0 页。
2. 把「触控目标 ≥44×44（行内按钮 ≥40）」写进 `DESIGN.md §10` 硬性约定第 5 条，并加一条 spec 锁住行内按钮尺寸类名。
3. 「表格移动端列模板」写入 §10.2 的组件级规则表，避免逐页各写一套。
4. 375 视口逐页截图纳入 CI 归档（本次脚本可直接复用，见附录）。
