# 结算/付款异常预警：取数成本量化（P1-4 第三阶段评估）

> 结论先行：**先做「缩小取数范围」，暂不做物化**。量化脚本已入库，可随时在真实库上复测。
> 相关代码：`server/src/modules/ai/anomaly/anomaly.service.ts` 的 `collect()`（9 处行级 `findMany`）、
> `anomaly-dataset.ts`（`buildAnomalyWhere` / `ANOMALY_SELECT`）、`rules-payment.ts`（9 条判定规则）。

## 1. 为什么这 9 处不能改 SQL 聚合

工作台/数据集那类「分组求和」早已改成 `aggregate`/`groupBy`（44 处 `@no-limit` → 32 处）。
剩下这 9 处是**逐单判定**：跨期累计（R1-a/R1-b/R2/R6）、清单量按链根归集后的明细重合度、
单笔与累计的先后关系——需要的是**每一行的金额/日期/编号**，不是「每组合计」。
换成 `groupBy` 不会报错，只会让规则**静默失效**（聚合结果照样跑通、结论变空）。

所以只剩两条路：**① 缩小取数范围**、**② 事实层物化**。选哪条取决于量级——于是先量化。

## 2. 怎么量（已入库，随时可复测）

```bash
# 在 server/ 下；--all 表示逐项目统计（刻意不跨项目混算，口径会失真）
npm run stats:anomaly-input -- --all
npm run stats:anomaly-input -- --project <项目id> --from 2026-01-01 --to 2026-12-31
npm run stats:anomaly-input -- --all --json     # 机读，便于画曲线
```

脚本口径与线上**完全共用** `buildAnomalyWhere` / `ANOMALY_SELECT` / `ANOMALY_ORDER`，
量出来的就是线上那条路径：**逐表行数 / 载荷 KB / 查询耗时 / 规则耗时 / 进程内存 / 规则命中数**。
**只读**：不写表、不调 LLM。

> ⚠️ 开发库通常只有几百行，量不出结论（本项目 dev 库实测：1 个项目 5 行 / 0.7 KB）。
> 要结论必须在**有真实数据的环境**跑 `--all`，把「行数最多的项目」那张表贴进本文件。

## 3. 合成压测曲线（本机 PG16 + 容器内 Node20）

夹具：每份合同 = 2 条合同物资 + 3 张结算单（各 2 条明细）+ 5 笔付款 + 2 张发票 + 2 张收领单
+ 1 张付款手续 + 1 张总结算书（2 条明细）。复现：

```bash
DATABASE_URL="postgresql://cms:cms123456@localhost:15432/cms_int?schema=public" \
  npm run seed:scale-fixture -- 3000      # 只允许写测试库（库名须含 test/int，脚本自带闸门）
```

| 合同数 | 取数行数 | 载荷 | 查询耗时 | 规则耗时 | 进程内存（取数后 → 判定后） |
|---|---|---|---|---|---|
| 200 | 3,400 | 0.8 MB | 115 ms | 14 ms | — |
| 1,000 | 21,000 | 4.6 MB | 332 ms | 67 ms | 80.8 MB → 86.6 MB |
| 3,000 | 63,000 | 13.9 MB | 908 ms | 216 ms | 141.1 MB → 146.8 MB |

**近似线性：每 1,000 份合同 ≈ 21,000 行 / 4.6 MB / 0.33 s 查询 / 0.1–0.2 s 规则 / +60 MB 内存。**

按此外推（同一套 9 条查询，单请求独占的内存与耗时）：

| 合同数 | 行数 | 载荷 | 查询 + 规则 | 内存 |
|---|---|---|---|---|
| 5,000 | ~105,000 | ~23 MB | ~1.5 s | ~200 MB |
| 10,000 | ~210,000 | ~46 MB | ~3 s | ~350 MB |
| 20,000 | ~420,000 | ~92 MB | ~6 s | ~650 MB |

单表占比（3,000 份合同那一行）：结算单（区间内 + 累计）**6.7 MB / 9,000+9,000 行** ≈ 全量的 48%，
付款流水 2.5 MB、发票 1.0 MB、合同物资 0.9 MB、总结算明细 0.8 MB、收领单 0.7 MB。

> **注意「累计口径」会随历史长度增长**：`settlementCumulativeWhere` 只设上界（区间之前的事实必须看见），
> 所以老项目（5 年历史）即使只看近 12 个月，结算单仍会**取全部历史**——这是成本随时间推移变大的根因。

## 4. 两条路的成本对比

| | 方案① 缩小取数范围 | 方案② 事实层物化 |
|---|---|---|
| 做法 | 强制期间（默认近 12 个月、上限 24 个月）+ 单次合同数上限（如 1,000），超限**明确报错/提示下钻** | 物化视图/汇总表（`mv_settlement_fact` 等），定时刷新，规则改取物化表 |
| 效果 | 成本从「∝ 项目全史合同数」变成「∝ 期间内合同数」；1,000 份 ≈ 0.4 s / 4.6 MB，**上限可控** | IO 下降（去掉 items / materialBase join），但**行数降不下来**（规则要逐单，聚合会丢单）；内存仍 ∝ 单数 |
| 改动面 | controller DTO 校验 + service 提前拒绝 + 前端提示文案；**规则层零改动** | 迁移 + 刷新任务 + 规则取数改源 + 一致性窗口 |
| 风险 | 低（只改入参边界）；需要业务确认「**拒绝**还是**截断并提示**」 | 中高：刷新延迟会让预警滞后；口径版本要定 |
| 工时 | 0.5–1 天 | 3–5 天（含迁移、刷新、回归） |

## 5. 结论与待业务确认

1. **先做方案①**：上限的作用是把「不可预测」变成「可预测」，且不碰规则层；
2. **方案② 暂缓**：它降的是 IO 不是行数，收益远小于「把范围限死」；等真实库里出现
   「单项目 > 3,000 份合同且需要看全史」的项目再上；
3. **需要业务拍两个点**（本文不替业务决定）：
   - 期间默认/上限取多少（建议默认近 12 个月、上限 24 个月）；
   - 超出上限时**直接 400 拒绝**，还是**截断到上限并显式提示「只分析了前 N 份合同」**（截断会让结论不完整，风险更高）。
