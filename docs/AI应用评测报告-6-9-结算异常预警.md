---

## 1. 一句话结论

**8 条规则在"结构真实、答案已知"的合成数据上全部命中、零误报，判定开销可忽略（毫秒级），
LLM 只在最后一步被调用一次（约 0.9 K tokens）**——也就是说这套预警在成本上几乎等于零，
真正的风险不在算力和费用，而在**规则口径与生产数据的贴合度**，这一点必须靠真实单据抽样解决（§6）。

---

## 2. 为什么用合成数据（评测边界，必须先说清）

生产库里**没有业务单据**：`Contract` / `Settlement` / `PaymentRecord` / `Invoice` 在 `cms` 库里
全部为 0 行（只有 85 个供应商主数据），所以"拿历史数据跑一遍、人工标 50 条"这条原计划无法执行。
数据库集成测试也被环境卡住（`cms-postgres-dev` 容器健康检查不通，Prisma 报 `P1001`）。

于是本次评测的**目标被主动缩小并说清楚**：

| 能证明 | 不能证明 |
|---|---|
| 8 条规则的实现与设计一致（每条都有针对性注入 + 真值对账） | 生产数据上的真实召回率 |
| 规则不会被"正常业务"误伤（干净合同零命中，且付款卡在比例上限边界上） | 真实单据的脏数据形态（缺字段、脏日期、跨币种） |
| 判定是纯函数、可复现、无隐藏状态、可被二次复算 | LLM 措辞质量（网关未配置密钥，`narrative.source` 走模板降级） |
| 规模-耗时曲线（决定"项目级全量扫描"是否可在线跑） | 端到端时延（无 DB、无网关，只测了判定与提示词拼装） |

**避免自欺的做法**：真值不写在测试断言里，而是由夹具生成时**同步登记**（`TruthItem`），
评分器按 `(规则码, 命中对象ID)` 严格对账——报错对象（报了个查不到的单据）不算命中。
另外评分器自身有校准用例：从真值里删一条，对应命中必须变成"误报"；凭空加一条真值，必须变成"漏报"。
否则"100% 召回"可能只是评分器太宽松。

## 3. 数据集设计

规模（`datasetStats()` 输出）：

| 合同 | 结算单 | 付款 | 发票 | 付款手续 | 收领单 | 终期结算明细 | 清单物资行 | 注入异常 |
|---|---|---|---|---|---|---|---|---|
| 12 | 61 | 63 | 62 | 5 | 61 | 1 | 24 | 9 |

注入分布（每个规则码占一份**独立合同**，互不重叠）：

| 规则码 | 注入 | 形态 |
|---|---|---|
| `R1_DUP_ACROSS_PERIOD` | 1 | 第 6 期新开一张结算单，金额/明细与第 1 期完全一致 |
| `R1_DUP_MATERIAL_QTY` | 1 | 清单量比累计结算量少 30（不新增单据，避免连带命中） |
| `R1_FINAL_SNAPSHOT_DRIFT` | 1 | 终期结算明细金额 = 月度结算 − 100 |
| `R2_OVERPAY` | 1 | 额外一笔 5 000～5 999 元付款，把累计推过 80% 上限 |
| `R3_PAY_WITHOUT_CONTRACT` | 2 | 一笔无 `contractId`；一笔指向不在本项目的合同 |
| `R4_INVOICE_MISMATCH` | 1 | 多开一张 666 元发票 |
| `R5_SETTLE_BEFORE_RECEIPT` | 1 | 收领单日期晚于结算日 15 天 |
| `R6_PROCEDURE_SNAPSHOT_DRIFT` | 1 | 付款手续开累付款比台账少 5 000 |

三条设计约束（也是踩过的坑）：

1. **注入互不串味**。给某合同加一笔付款，会让该合同付款手续的"开累快照"与台账失配 → R6 连带命中。
   所以**注入合同一律不生成付款手续**，手续只出现在专用于 R6 的合同与干净合同上。
   同理 R1-b 不走"改结算金额"的路子（那会连带命中 R4/R2），而是裁低清单量。
2. **干净合同必须真干净**：各期金额互不相同（防 R1-a 误命中）、发票与结算等额、
   收领单早于结算日、**累计付款恰好等于上限**（`≥ limit` 会误报，`= limit` 必须不报，这条边界专门用来试容差）。
3. **确定性**：`mulberry32(seed)` 代替 `Math.random`，同 seed 两次生成必须逐字节一致
   （有单测锁死），否则评测结论无法被同事复算。

## 4. 结果

### 4.1 规则层

- 注入 9 条，命中 9 条，漏报 0 条，误报 0 条
- 召回率 **100.0%**，准确率 100.0%

| 规则码 | 注入 | 命中 | 漏报 | 误报 | 召回 |
|---|---|---|---|---|---|
| R1_DUP_ACROSS_PERIOD | 1 | 1 | 0 | 0 | 100.0% |
| R1_DUP_MATERIAL_QTY | 1 | 1 | 0 | 0 | 100.0% |
| R1_FINAL_SNAPSHOT_DRIFT | 1 | 1 | 0 | 0 | 100.0% |
| R2_OVERPAY | 1 | 1 | 0 | 0 | 100.0% |
| R3_PAY_WITHOUT_CONTRACT | 2 | 2 | 0 | 0 | 100.0% |
| R4_INVOICE_MISMATCH | 1 | 1 | 0 | 0 | 100.0% |
| R5_SETTLE_BEFORE_RECEIPT | 1 | 1 | 0 | 0 | 100.0% |
| R6_PROCEDURE_SNAPSHOT_DRIFT | 1 | 1 | 0 | 0 | 100.0% |

附带的两个"静默正确性"断言：干净合同（c09～c12）命中数为 0；`notEvaluated` 为空
（每条合同的付款比例都能解析出来，不存在"压根没判"的黑洞）。

### 4.2 规模与耗时（单进程、无 DB，冷启动后同进程计时）

| 合同数 | 结算单 | 付款 | 判定耗时 |
|---|---|---|---|
| 12 | 61 | 63 | 5.2 ms |
| 50 | 251 | 253 | 11.1 ms |
| 100 | 501 | 503 | 13.7 ms |
| 200 | 1 001 | 1 003 | 20.1 ms |
| 400 | 2 001 | 2 003 | 41.8 ms |
| 800 | 4 001 | 4 003 | 101.6 ms |

结论：**线性增长，4 000 张结算单 ≈ 0.1 s**，项目级全量扫描在线跑没有压力。
唯一超线性的是 R1-a（同合同内两两比较），它的风险不在"合同数"，而在"单个合同的结算单张数"——
合同链条再长也只有几十张，可忽略；但若将来有人把跨项目结算单塞进同一个 `contractId`，要回头看这里。

### 4.3 成本

| 项 | 实测 |
|---|---|
| 规则层 token | 0（纯计算） |
| 措辞层调用次数 | 1 次/份报告（命中清单不截断，一次给完） |
| 提示词规模 | 1 991 字符 ≈ 905 tokens（12 合同 / 9 条命中） |
| 报告规模 | 结论 120~200 字 + 3~5 条动作建议 |
| 配额 | 复用 `AiQuota`（默认每小时 20 次，可配），失败即退款 |

也就是说：**一次完整扫描的边际成本 ≈ 一次短对话**。真正的开销在使用频率，不在算法。

## 6. 已知局限与下一步

1. **生产召回率仍未测**（最重要）。数据补齐后的动作是确定的：
   把 `cms` 库 8 张表按 `anomaly.service.ts` 的 `select` 导出成 JSON → 直接用 `scoreFindings()`
   对账人工标注的 50 条真值。评分器与真值结构已经就绪，不需要改代码。
2. **脏数据形态未覆盖**：金额为 0 / 负数、`settleDate` 为空、跨币种、同一合同多链段并行。
   其中"结算日期为空"目前是**跳过不判**（不误报，但会漏），已在 `notEvaluated` 语义里留了口子。
3. **R1-b 口径假设**：清单量按合同链根聚合、容差 2%。若业务实际允许"先超量结算后补清单"，
   这条会持续报"需复核"，需要业务确认后调 `ai.anomaly.qtyTolerancePct`（参数化，已留）。
4. **LLM 措辞质量未评**：网关无密钥，只能验证降级链路。配好密钥后应补一次人工打分
   （结论是否点名到单据、动作是否可执行、有没有编数字）。
5. **前端渲染未截图验证**：容器内无浏览器。面板逻辑与构建已通过，但"人眼一看"这一步没做。

## 7. 复现方式

```bash
cd server
npm run test:anomaly        # 规则单测 + 措辞单测 + 本次评测（含评分表）
```

评测数字不是手抄进文档的：`scoreToMarkdown(scoreFindings(evaluatePaymentAnomalies(input), truth))`
就是本文件 §4.1 那张表的来源，`aiAnomalyBench.spec.mts` 里断言了召回 100% / 误报 0 / 覆盖 8 个规则码。
数据集换 seed 只影响随机量（R2 的超付额），规模与真值条数不变——这一点也有单测锁死。

### 7.1 真实单据上的召回率：执行链路已就位（2026-10-23 补）

本文件评的是「实现是否与设计一致」，**不是真实单据召回率**。后者只差数据，不缺代码：

```bash
cd server && set -a && source .env && set +a
npm run anomaly:export -- --project <项目id> --out tmp/anomaly-dataset.json   # 只读导出 8 张表 + 规则初判候选
# 人工标注 tmp/anomaly-truth.json：逐条 hit: true/false，hit=false 必须写 note
npm run anomaly:score -- --dataset tmp/anomaly-dataset.json --truth tmp/anomaly-truth.json \
  --min-recall 0.9 --max-fp 2 --out docs/AI应用评测报告-6-9-结算异常预警-真值对账.md
```

评分时用导出的 `rows` **重算规则**（不信候选），所以报告永远描述当前代码；门槛不达标脚本退非 0。
标注纪律、防自欺设计与冒烟验证见 `docs/AI应用落地计划.md` §10。

## 复核更正（2026-10-23 晚）

`docs/AI应用审计报告-2026-10-23.md` §8 复核时发现：**上面「评测口径 = 线上口径」这句当时并不成立**。
`server/scripts/export-anomaly-dataset.mts` 原先没取 `cumulativeSettlements`、没给
`buildPaymentAnomalyInput` 传判定区间、也没把系统参数里的容差传进 `evaluatePaymentAnomalies`，
于是同一份数据在评测里会多报出线上不会报的规则（实测：线上 0 命中，评测命中 `R3_PAY_WITHOUT_CONTRACT`）。

脚本已改为与线上同一条取数路径与同一套容差。本报告里的召回率/误报率数字仍然只描述
`anomaly-bench.ts` 的合成夹具，**不能**当成生产召回率——这一点原报告已声明，仍然成立。
