**实现期纠正的两处方案假设（`@container` 条件的 `var()`）**

方案原打算「`@container` 里的断点值引用 `:root` 的 CSS 变量」。**实测不成立**（2026-10-15，Edge headless + CDP
探针，变量定义在 `:root` 与容器元素自身两种写法都试过）：`@container (max-width: var(--cq-md))`
**整条规则被浏览器丢弃**；同一条写 `720px` 或 `calc(720px)` 均正常升降级。
故单一事实源落在 TS 常量 `CONTAINER_BREAKPOINTS`，`--cq-*` 退为 CSS 镜像，三处一致由 §5 的锁保证。
→ **§5 ②、§3 阶段 1 的"引用 CSS 变量"措辞据此更正**（下文已标）。

**实现期发现并修掉的一处静默失效（`useContainerWidth`）**

第一版 `useContainerWidth()` 用 `useRef` + `useEffect([])` 挂观察器，**在容器是条件渲染时会永远挂不上**：
`TaskViewModal` 的正文（`{detail && <div ref={cqRef} className="cq">}`）要等详情接口回来才渲染，
而 `useEffect` 只在挂载时跑一次、那时 `ref.current` 还是 `null` → 直接 return，之后再无机会。
后果是**静默的**：容器压到 600px，`Descriptions` 仍渲染 2 列（构建、单测、类型检查全绿）。
修法是改用**回调 ref**（`useCallback`）——元素每次挂载/卸载都会通知，条件渲染也能观察到。
该陷阱已写进 [.claude/rules/frontend-conventions.md](../.claude/rules/frontend-conventions.md)。

**实现期发现并修掉的第二处静默失效（portal 切换不重挂载）**

阶段 5 把 `RichTextEditor` 的全屏层改成 portal 到 body 之后，**编辑区内容会丢**：
portal 只换了 DOM 挂载点，**组件实例并没有重挂载**，于是"外部 value → 编辑区"那个
`useEffect([value])` 不会重跑，新渲染出来的 `contentEditable` 是空的。
最阴的是**表单里其实存着值**（点确定不报"请输入条款内容"），只有 DOM 空了 —— 构建、单测、类型检查全绿。
修法：该 effect 的依赖补上挂载点状态（`[value, fullscreen]`）。
2026-10-15 真渲染验收抓到（逐字符派发真实 `char` 事件打 15 个字 → 点全屏 → 断言内容仍在），
并加锁防回归。

**实现期纠正的第三处判断（筛选区列数不能直接套断点）**

`ModuleListPage` 的筛选区最初按容器套 480/720/1024 三档算每行字段数，结果 1280 桌面从 4 列掉成 3 列：
**容器比视口窄掉整个外壳**（侧栏 220 + 边距，1280 只剩 ~996），每一档都被往下挪了一格。
改为按布局约束推 ——「每行 = 容器宽 ÷ 240px，下限 2 上限 4」—— 三档视口下的结果与 DESIGN.md §10 完全一致
（375 → 2 列 · 768 → 3 列 · 1280 → 4 列），且不引入第二套断点。

  **没有**逐个挂 `.cq`（不需要）。
- 弹窗内的 `Descriptions column`（如合同详情弹窗）：仍是固定列数，未接 `useContainerWidth()`

## V1 的局限（V2 的出发点）

V1 全部基于**视口**判断（`useResponsive()` 读的是 window 宽度、AntD `Col` 的断点是媒体查询）。
但"视口宽度"并不等于"组件可用宽度"：同一个组件在不同的**容器**里表现天差地别，而 V1 对此无能为力。
V2 就是为这一类问题立的规矩。

## 1. 目标与双层响应式模型

### 1.1 强制条款

> **所有布局必须通过 Container Queries 实现组件级响应式，而非仅依赖全局断点。**

即：**组件自身的布局（列数、方向、密度、显隐）由它所在的容器宽度决定**，不得用"窗口宽不宽"去猜"我这里挤不挤"。

### 1.2 双层模型（不是二选一）

| 层 | 判定依据 | 机制 | 负责什么 |
|---|---|---|---|
| **页面级（保留 V1）** | 视口宽度 | 媒体查询 / AntD 断点 prop / `useResponsive()` | 应用外壳：侧栏（固定 ↔ Drawer）、顶栏精简、内容区边距、**页面级栅格的列数** |
| **组件级（V2 新增，强制）** | **容器宽度** | `container-type` + `@container` + `useContainerWidth()` | 组件内部：卡片内列数、工具条折行、表格/图表在窄容器下的降级、预览区、抽屉/弹窗内的表单与表格 |

两者**并存**：外壳只能看视口（它的容器就是视口）；组件必须看容器（它不知道自己会被放到多宽的地方）。

### 1.3 为什么必须做（本仓库的真实场景）

| 场景 | 现在（视口驱动）的问题 | V2 的做法 |
|---|---|---|
| 同一张表出现在**整页**与**900px 弹窗**里（`TaskViewModal`、`PreviewPublishModal`） | 视口宽 → 按"宽屏"渲染，在弹窗里挤压破版 | `@container` 按弹窗宽度降级（隐藏次要列/紧凑行高） |
| 工作台统计卡：`lg=16` 主列 + `lg=8` 侧列 | 侧列卡片只有 ~380px 宽，却按"桌面"渲染，内部图例挤成两行 | 卡片读自身宽度，窄则改纵向堆叠 |
| 同一表单放进**抽屉**（≤md 的 Sider）或**弹窗** | 视口可能很宽（桌面 + 侧栏抽屉），表单却是单列宽度 | 表单按容器宽度决定 `label` 位置与列数 |
| 合同/模板**预览区**（`.doc-preview`）在弹窗与全屏两种容器里 | 只能按视口猜 | 预览区按容器宽度调 padding 与字号 |

## 2. 技术约束（先认清边界，再谈落地）

> 这一节是方案能落地的关键：**Container Queries 不能驱动 AntD 的响应式 prop**，必须分层使用。

1. **AntD 的断点 prop 是视口驱动的**：`<Col xs/md/lg>`、`Table` 的响应式行为、`Grid.useBreakpoint()`
   全部走媒体查询，**无法被容器宽度驱动**（antd 5.29 尚无 CQ 集成）。
   → 结论：**页面级栅格继续用 AntD 断点 prop**（它就在视口级这一层，语义正确）；
   **组件内部布局改用自定义 class + `@container`**，不要再用 `useResponsive()` 的值去推断容器。
2. **JS 需要容器宽度时**用 `ResizeObserver`：新增 `useContainerWidth(ref)`（只测自己的容器），
   供"条件渲染 / 传 `size` / 算 `scroll.x`"这类 CSS 表达不了的场景。
   仍然**禁止** `window.innerWidth` / `matchMedia`（避免第二个断点来源打架）。
3. **`container-type` 的布局 containment 有副作用**：被设为容器的元素会成为其后代
   `position: fixed/absolute` 的**包含块**，也会影响 `overflow` / `sticky`。
   → 自绘浮层必须走 portal（AntD 默认 portal，安全）；**`Sider` 的 `position: sticky` 不要放进 CQ 容器内**。
   落地实例：`RichTextEditor` 的全屏层为此改为 `createPortal(frame, document.body)`
   ——弹窗正文自阶段 5 起就是容器，就地 `fixed` 必被截住（§0.2）。
   ⚠️ 附带一个 portal 特有的坑：**portal 切换不会重挂载组件**，只依赖 `[某状态]` 的 effect 不会重跑，
   内容回填要显式依赖"挂载点"状态。
4. **CQ 规则必须写在样式表里**（`@container` 无法纯内联表达）——这与现行
   [DESIGN.md](../DESIGN.md) §9「全站只有两个样式文件」冲突，需按 §6 改写该条。
   → ✅ 已按 §6 改写，落点 `web/src/styles/containers.css`（DESIGN.md §9 已允许）。
   ⚠️ 补充实测结论：`@container` 的**条件本身也不支持 `var()`**（§0.2），断点只能写字面值。
5. **浏览器基线**：Container Queries 需 Chromium 105+ / Safari 16+ / Firefox 110+。
   **前置检查**：确认实际客户端浏览器基线（企业内网若仍有旧内核浏览器，需先定降级策略：不支持的浏览器回落到 V1 的视口行为，即"渐进增强"，不阻塞可用性）。
   → ✅ 已定：只保现代浏览器；写法上"宽容器 = 基线、窄容器才覆盖"天然满足渐进增强，故不写 `@supports`、不加 polyfill。
6. **CQ 不解决数据密度**：36 列台账在窄容器里依然只能横向滚动（V1 §6 的取舍继续有效）。

## 4. 验收（容器级，不只是切视口）

> V1 的验收是"切三档视口看页面"；V2 必须**在视口不变的前提下改变容器宽度**，否则测不到 CQ 是否生效。

- **同一视口（如 1280）下**：
  1. 打开 900px 宽的弹窗（`TaskViewModal` / 预览弹窗），断言其中的表格/表单进入"窄容器"形态；
  2. 把同一张表分别放在整页与弹窗里，断言两者**形态不同**（这正是 CQ 与视口断点的判别点）；
  3. 工作台在 `lg=8` 侧列卡片与整行卡片两种宽度下，断言图表图例/统计卡排布不同。
- 手法沿用 Edge headless + CDP（见 [docs/development.md](development.md) §5.2）：用
  `Emulation.setDeviceMetricsOverride` 固定视口，再通过 `Runtime.evaluate` 改容器宽度（拖拽分隔条或直接设 `style.width`）
  后截图对比；同时断言页面上**不出现横向溢出**（`scrollWidth <= clientWidth`）。
- 回归：`cd web && npm run build`、`cd server && npm test`（含新增的 CQ 漂移锁，见 §6）。

## 5. 防漂移（把"必须用 CQ"变成机器可查）

- **新增 `server/test/containerQuery.spec.mts`**（源码扫描，无 DB）：— ✅ 已完成，实际落了 6 条判据
  ① 组件内部**不得**用 `useResponsive()` 的视口值决定自身布局（白名单放页面外壳层文件，
  过渡豁免条目必须注明"何时删除"）；
  ② `@container` 里的断点值必须来自 §阶段 1 的 CSS 变量（不得写裸 `px`）；
  > ⚠️ **更正**：`var()` 在 `@container` 条件里不被解析（§0.2），故判据改为
  > "只能写字面值，且字面值必须等于 `CONTAINER_BREAKPOINTS`"，同时校验 `containerSize.ts` ↔ `--cq-*` ↔ 规则三处一致。
  ③ 使用 `container-type` 的组件必须挂上规范类名；
  > 并加固为"`container-type` 只许出现在 `web/src/styles/*.css` 的 `.cq` 上"（内联样式里挂会被挡）。
  ④ 新增：`styles/containers.css` 必须在 `index.css` **之后**引入（同特异度规则靠顺序压过基线）；
  ⑤ 新增：渲染 `.doc-preview` 的组件必须挂 `.cq` 容器（否则容器查询无处可查）。
  ⑥（阶段 3–5 补）`.col-secondary` 的声明与隐藏规则必须成对存在（改名即静默失效）；
  ⑦ `container-type` 只许挂 `.cq` / `.ant-modal-body` / `.ant-drawer-body` 三者；
  ⑧ 窄容器表单栅格的覆盖**不得含 `.cq`**（否则页面级筛选区的"手机 2 列"会被误降为单列）；
  ⑨ `RichTextEditor` 必须 portal 全屏层、且内容同步 effect 依赖 `fullscreen`。
- 与 [CLAUDE.md](../CLAUDE.md)/[.claude/rules/frontend-conventions.md](../.claude/rules/frontend-conventions.md)
  的"断点唯一来源"表述一起改（视口层归 `useResponsive()`，容器层归 CQ/`useContainerWidth()`）。— ✅ 已完成

## 7. 风险与取舍

- **改造面广**：涉及弹窗/表格/卡片/表单四族，且 V1 的视口判断与 CQ 判断会在一段时间内共存 →
  **按 §3 分阶段灰度**，每阶段跑 §4 的容器级验收。
- **两套断点并存的认知负担**：必须靠 §5 的锁 + DESIGN.md 的双层模型把它讲清楚，否则容易出现
  "同一个人一会儿用视口一会儿用容器"。
- **容器化 containment 的副作用**（§2.3）：`fixed` 包含块与 `sticky` 失效风险，改造时要逐处确认。
- **不做**：36 列台账卡片化（沿用 V1 取舍）；不引入第三方 CQ 库/PostCSS 插件（保持现有构建链）。
