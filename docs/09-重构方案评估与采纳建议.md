结算驱动付款 → 台账实时聚合 → 审批可配置 → 全链路留痕**。

| 判断 | 结论 |
|---|---|
| 方向 | ✅ **正确**——"以合同为核心的履约与资金闭环"是本项目的合理演进方向 |
| 指导性 | 🟡 **中上**：约 **1/3 的主张本项目已经做到**（方案未读代码，通篇"可能/建议 ensure"） |

## 3. 已具备明细（方案为何会误判）

方案写作时**未阅读本仓库代码**——其行文大量使用"当前…可能是""建议 ensure 确保"，属于通用重构建议书的措辞。
典型误判与实情：

- **"台账可能只是聚合视图"** → `ledger.service.ts:39-60` 已是标准批量聚合（一次查询 + 内存 groupBy，注释明确
  "避免 N+1"），且 `calcCompliance()`（`:178`）**自动**计算合规问题、**不落库**。
- **"避免在业务表中冗余金额字段"** → `Contract` 上根本没有 `settledAmount/paidAmount` 这类冗余列，
  累计值（开累结算/付款/开票）全部在台账里实时聚合。
- **"合同只是招采完成后的结果表"** → 合同的 `taskId` 只是"来源"，其下游已挂结算/付款/发票/还款/收领单/
  日报/资产台账/物资清单/变更日志；唯一的"断点"恰恰是 §2.2 A（现场确认）。
- **"锁定 PostgreSQL、清理 MySQL 兼容注释"** → PG 单 schema 已于 2026-09-17 完成；`README.md` 里那段
  MySQL 差异 FAQ（属文档性残留）也**已于 2026-10-14 删除**——库选型只有一种，不该给后来者留"切换"暗示。

> 结论：**方案的方向描述与项目现状高度一致**，这反过来印证了现有架构选择是对的；
> 但它把"已完成"当"待做"，因此**不能按它的路线图（1–4 阶段、约 10 个月）整体执行**。

## 4. 真缺口明细与依赖关系

```
A 现场确认 ──(已实施)──> 闸门：未确认的现场记录不计入结算口径
                             │
                             └── 效力上限受 E 制约：Settlement 无清单项级数量，
                                 故"结算只能取已确认量"要等 E 落地才彻底

B 防超结/防超付 ──(已实施)──> 金额级上限（含补充协议链）
                             └── 量级校验（结算量 ≤ 已确认量）同样依赖 E

D 变更/签证结构化 ──> 决定"合同当前金额"口径 ──> B 的上限才准确
E 清单项级结算明细 ──> 依赖 D 的口径 ──> A 的闸门才彻底、量级校验才可做

C 采购清单→合同清单衔接（独立，可并行）
F 审批流（独立，依赖业务需求）
H 金额计算补测（独立，成本最低）
```

- **A 的诚实边界**：本轮闸门的实际作用点是 ①`contract-settled-qty`（补充协议起草的"已结算量"）
  ②日报列表的确认状态与筛选 ③结算弹窗的"未确认现场量"提示。**不是**"结算单取数已被硬闸门拦住"——
  那需要 E。
- **D 是口径分歧点**：项目用**补充协议**表达合同变更，方案用**变更单**。两者并存会造出两套"合同当前金额"，
  必须先澄清（§7）再动手。

**依赖关系更正（2026-10-15 复核）**

上面那张图把 `E ──依赖──> D` 画成了硬依赖。**代码层面它不是硬的**：

- D 决定的是**口径**（"未形成补充协议的签证算不算进可结量"）；
- E 的**机制**可以独立落地：清单项级结算明细的基线可直接取**合同链的 `ContractMaterial` 求和**
  （与 `contractChainAmount()` 同一形状；补充协议本身也是合同、自带清单行）。
- 所以 **E 可以先做**，前提只是业务接受"暂不含签证增量"这一口径。把 E 记成"D 的附属品"会让它无谓地等下去。

⚠️ 但有一处**必须一起处理**：`SettlementLedger` 是**派生**表（由结算 / 发票 / 保理 / 逾期
按 `contractId + 月` 合成，见 `settlement.service.ts` 的 `computeLedgerAutoFields` 与 upsert 段），
E 若不与这条派生链对齐，就会再添第三套口径。

## 5. 与既有决策冲突的 4 项（含替代方案）

### 5.1 付款三级模型（最关键）

- **方案**：`PaymentPlan`（计划）→ `PaymentRequest`（申请）→ `PaymentRecord`（实际付款）+ 核销，付款计划由结算生成。
- **项目**：曾完整实现过这套模型，后**有意收敛为单表 `PaymentRecord`**（付款台账），并在 `docs/07` §3.2
  明确"发票 ↔ 付款无核销关联，**不做三单匹配**"。保留的 `applyId` 死字段已在 2026-10-13 的 P1 批次删除。
- **判断**：这是**产品口径**问题，不是技术优劣问题。**维持现状**，除非业务明确要求"按计划核销 + 三单匹配"。
- **若将来要做**：按 `docs/05` §9 的路径先补"行级数据范围"，再独立立项，且需说明现有单表为何不满足。

### 5.2 数据库枚举

- **方案**："核心业务枚举（合同类型、结算状态、付款状态）建议用数据库枚举或独立表"。
- **项目**：铁律 4 —— 所有枚举/下拉走 `dict_type`/`dict_item`，业务表存**字典项编码字符串**；
  全库仅保留一个 `ContractType` enum。字典驱动带来的是"业务可维护的选项、颜色、排序、联动"。
- **判断**：**不采纳**。方案自己也留了"UI 配置类字段继续用字典"的口子，本项目的字典已是"配置类 + 业务枚举"的统一形态，
  改成 DB enum 是纯倒退。
- **2026-10-14 补充（回应其合理内核）**：该主张背后的真实痛点是**"code 以裸字符串散落各处"**——
  审计证实：结算/付款/发票状态字面量散落在各 service 约 48 处，`contract.service.ts` 还自己定义了一套
  `STATUS_DRAFT/APPROVING/SIGNED`（与 `constants/workflowGuards.ts` 的 `CONTRACT_STATUS` 重复），
  而 `Contract.contractType`（DB enum）与 `Contract.typeCode`（dict 编码）**同一取值空间存两份**、
  写入处用 `as any` 绕过类型检查。**处置**：不动数据库形态，改走
  「**常量单一事实源 + 漂移锁**」——`server/src/constants/statuses.ts` 收敛 code，
  `server/test/statusCodes.spec.mts` 双向锁「常量组 ↔ 字典项 ↔ schema enum」（见 §8.4）。

### 5.3 供应商快照（理由成立，方向需澄清）

- **方案**：`ContractSupplierSnapshot` 保存签订时的法人/联系人/银行账户，避免主数据变更影响历史合同。
- **项目**：铁律 5 —— 合同只存 `supplierId`，法人/联系人/银行由供应商库**实时关联**。
- **冲突的真实性（这是方案最有价值的一条）**：合同正文导出走 `template.service.generate()`，其中
  `银行名称: sup.bankName`、`法人姓名: sup.legalPerson`、`联系人电话: sup.contactPhone` 等**取的是实时值**；
  供应商主数据一改，**历史合同再导出内容就变了**。
- **更值得注意的证据**：项目其实**声明过**对应策略——系统参数 `supplier.name.sync.history`
  （`KEEP 保留原值 / SYNC 同步更新`，见 `server/src/seed-data.ts:280`），但**全仓无任何读取点**，
  即该策略**从未实现**。所以"快照 vs 实时"在本项目里是一个**悬空的语义问题**，方案恰好点中了它。
- **建议**：先澄清（§7 ②）。若确认要"签订时快照"，**最小实现**是在 `contract.service.sign()` 时
  把供应商关键字段快照进合同（复用现有 `formData` 或新增 `supplierSnapshot` 文本列），
  **不改**"合同主表只存 supplierId"的结构；顺带把悬空的 `supplier.name.sync.history` 参数删掉或实现。

### 5.4 Flowable / 物化视图 / Redis / MQ

与 `docs/05` 的既有结论一致，不再重复论证：**Java 工作流引擎与本栈（NestJS）不匹配**；
**单库单实例不需要分布式事务**；**本项目数据量下内存聚合 + 索引足够**，物化视图会引入刷新延迟与一致性负担。

### 9.1 变更结构化 + 合同当前金额（答复 ③）

- **口径**：**合同当前金额 = 主合同金额 + Σ 补充协议 `changeAmount`**（`changeAmount` 为**带符号增量**，
  降价/减项为负）。单一实现在 `common/utils/contract-chain.ts`（`resolveChainAmounts()`），
  防超结上限 `contractChainAmount()` 复用同一实现——**上限与"当前金额"不可能再分叉**。
- ⚠️ **为什么不能用补充协议的 `amount` 求和**：它是自由填写字段，涨价/降价时用户往往填"剩余数量 × 新价"，
  而主合同里那部分数量的原值**已经计过一次** → 直接相加会重复计入。
  故新增 `common/utils/supplement-delta.ts`，在**发布时**按"补充协议清单 vs 主合同清单"服务端重算：
  涨价/降价取价差×数量、增数量取原价×增量、新增物资取全额、未知类型一律 0。
- **存量回填**：迁移里 `UPDATE ... SET changeAmount = amount WHERE isSupplement='Y'` ——
  存量补充协议可能没有清单行，无法反推差额；按原 amount 迁移可保证上限**不因改造而缩水**，
  下次保存清单时再重算为真正的增量。
- **链 IO 搬家**：`contractChainRootId/Ids/Amount`、`chainSettledTotal/chainPaidTotal` 从 `amount-guard.ts`
  移到 `contract-chain.ts`。原因：`amount-guard` 被 `.mts` spec 加载、**不能新增相对 import**（仓库硬约束），
  而"上限"必须复用链口径。`amount-guard` 现在只做不碰 db 的策略与比较。
- **测试**：`contractChain.spec.mts`（含"从补充协议出发解析到同一条链""只算直接补充协议""主合同未填 → null"
  "防环"）、`supplementDelta.spec.mts`（含"涨价只计差额"这条核心回归）；原 `amountGuard.spec.mts` 的链用例随之搬移。

### 9.2 红/黄预警（答复 ③）

- `common/utils/amount-alert.ts`：红 = 结算 > 当前金额×110% 或 补充协议 > 主合同×130%；
  黄 = 80% / 110%。**严格大于**（恰好等于阈值不预警）。阈值是业务规则，写进代码常量而非 `sys_param`
  （改阈值走代码评审 + 版本记录）。
- **展示**：`GET /dashboard/reminders` 增 `amountAlerts`（红在前，最多 20 条 + `amountAlertTotal`）；
  工作台新增「合同金额预警」卡片。**只做展示**，不拦截单据、不改 `*_over_amount_policy` 策略。
- 分母未知（合同未填金额）时**不报**——"未填"不能当 0，宁可漏报不误报。
- **分子口径是有意选择**：预警用**结算单口径**（`Settlement.actualAmount`，与防超结闸门同源），
  而台账那列「已结算金额占合同比例」的分子沿用台账自己的「开累结算金额」
  （`SettlementLedger.monthSettleAmount`，它还含发票/保理/逾期派生）。两者在业务上不是一回事：
  闸门与预警回答"有没有超结"，台账回答"这条链的账现在是多少"。实测当前数据两者**逐条相等**
  （如 HT-2026-0001 均为 2,137,599.77），故不额外澄清；若将来某月只有发票/保理而没有结算，
  两者会分开，届时应以台账列为准并在预警里说明分母。
