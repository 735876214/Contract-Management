# 05 · 四域扩展可行性评估（决策记录）

> **文档状态**：架构可行性评估 + 决策记录，2026-10-13 定稿。
> **基准**：现有仓库 `Contract-Management`（main @ `0755e7c`）+ 业务方澄清后的收窄范围。
> **性质**：评估结论与设计建议，**尚未实施**；实施时需另出实施计划。

## 0. 摘要（TL;DR）

业务方提出「**招标 / 合同 / 采购 / 进出场**」四域一体化平台方案（Spring Boot 3 + Vue 3 + 微服务 +
Redis/MQ/MinIO/Flowable/Seata + 电子签章 + 低代码）。经范围澄清后：

| 判断 | 结论 |
|---|---|
| 整体可行性 | ✅ **可行**，且**推荐在现有系统上增量扩展**，而非重写 |
| 技术栈 | ✅ **沿用现有**（NestJS 10 + Prisma/PostgreSQL + React 18 + AntD 5）；**不换栈** |
| 微服务 / 网关 / Redis / MQ / MongoDB / Seata / Flowable / 电子签章 | ❌ **均不需要** |
| 主要增量 | **约 6 张新表 + 1 个外键字段 + 若干页面**，全部在现有栈上完成 |

一句话：**收窄后的需求，约八成能力现有系统已具备可直接复用**。

## 1. 背景与收窄后的范围

原方案规模远超现有系统（新增"招标域""进出场域"，并整体换栈）。经澄清，范围收窄为：

| 域 | 做什么 | 明确不做 |
|---|---|---|
| **招标** | 各环节的**文件与信息流转留痕**（立项/文件/公告/投标/评标/定标） | 在线开标评标、加密递交、专家库、外部平台对接 |
| **合同** | 起草、签章、变更、**履约跟踪**、**归档**、**与采购订单联动** | 电子签章集成 |
| **采购** | 现有采购工作流 **+ 下游**：采购订单、到货验收、对账结算 | 重建 P2P 申请/询比价 |
| **进出场** | **只做物资进出场**，复用现有 **收领单/日报/资产台账** | 人员/车辆进出场、独立表、门禁/人脸/RFID、扫码 |

> 收窄后，原方案的"重写 + 微服务"前提**不再成立**，评估从"高风险重写"转为"**现有系统上的增量扩展**"。

## 2. 组件选型总表

| 组件 | 结论 | 关键理由 |
|---|---|---|
| Spring Boot / Vue（换栈） | ❌ 不换 | 现有 22 模块 / 50 模型全部作废，无技术必要性 |
| 微服务 + API 网关 | ❌ 不需要 | 无多团队独立交付 / 独立扩缩容 / 强隔离压力；nginx 反代已够 |
| Redis | 🟡 按需 | 单实例下进程内缓存（dict/sys-param）已够；JWT 无状态无需 session |
| RocketMQ / RabbitMQ | 🟡 按需 | 单体同库事务强于 MQ 最终一致；已有 `ImportTask` 作 DB 队列范式 |
| MongoDB | ❌ 不需要 | 附件要的是**对象存储**；灵活字段用 **PG jsonb** 即可 |
| MinIO（对象存储） | 🟡 按需，推荐 | 唯一有实收益的存储演进；落盘写入点有 3 处（上传 / 合同签章件 / 导入错误报告），**已统一收敛到 `common/services/storage.service.ts`**，换实现即换存储 |
| Flowable（工作流引擎） | ❌ 不做 | **业务已确认不需要多级流程**（2026-10-16）；且 Java 生态与现有栈不匹配（分析留痕见 §5） |
| Seata（分布式事务） | ❌ 不需要 | 单库事务足够 |
| 电子签章 | ❌ 不做 | 业务方明确不需要 |
| 低代码平台 | ❌ 一期不做 | 已有字典/模板/列配置三层配置化；可做受控 L1 折中 |
| DB 主从 / 读写分离 / 备份 | 🟡 按需（运维） | 先落实定期备份 |
| 全文检索 | 🟡 可选 | 用 PG `tsvector`/`pg_trgm` 起步，不必 Elasticsearch |

## 3. 逐域可行性（可复用 vs 需新增）

### 3.1 招标管理 → **并入现有采购工作流（设计 A）**

**关键发现：现有「采购工作流」本身就是一个招标流程**，已覆盖方案招标域的大部分：

| 方案招标域表 | 现有对应 | 重合度 |
|---|---|---|
| `tender_project` | `ProcurementTask` | 高 |
| 招标文件 | `ProcurementDocument` + `ProcurementTemplate` | 高 |
| 公告发布 | `ProcurementNotice` | 高 |
| `tender_bid` | `ProcurementResultReport.suppliers`（**JSON 字符串**） | 中 |
| `tender_evaluation` | `reviewMembers`(文本) + `candidates`(JSON) | 中 |
| 定标 → 合同 | `generateLinkedContract()` + `resolveContractUnits()`（已实现、已单测） | 高 |

**决策：设计 A**（详见 §6）——不另起平行域，只补结构化缺口。

### 3.2 合同管理 → 增强现有

- **已具备**：起草（`ContractDraft.tsx`）、模板与变量、变更留痕（`ContractChangeLog`）、
  状态（DRAFT/APPROVING/SIGNED，其中 APPROVING 的含义是**已提交、待上传签章件**）、
  补充协议链、驳回回起草、台账聚合（`ledger.service.ts`）。
- **需新增**：履约跟踪、与采购订单联动、归档（详见 §10）。
- **不做**：电子签章。

### 3.3 采购管理 → 补充下游（详见 §7）

- **已具备**：采购工作流全链（`procurementFlow.ts`）；定标结果在 `ProcurementResultReport.candidates`；
  已能自动生成草稿合同。
- **需新增**：采购订单、对账单；**到货验收复用现有收领单**。

### 3.4 进出场管理 → **只做物资（复用现有，几乎零改动）**

**发现：本项目的"进出场"在代码里就是"物资进出场"，且已大部建模**（详见 §8）。
**决策：只做物资进出场**——不建表、不做人员/车辆；复用 `AssetLedger` + `DailyReport` + `ReceiptOrder`。

## 4. Redis 与多副本部署

**结论**：**多副本的阻塞项不是 Redis**，而是「文件本地磁盘 + 进程内缓存 + 编号竞态」三项。

**已天然安全的部分**：无状态 JWT（**无需 session**）、业务状态全在 PG、乐观锁 `assertVersion`（29 处）、
`@@unique` 唯一约束、`ImportTask` 状态落库、通知/日志在 DB。

**真正阻塞多副本的三项**：

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| ① | **文件本地磁盘**（最大） | `main.ts` `useStaticAssets(UPLOAD_DIR, '/api/files')` + multer 落盘 | 副本 A 上传，副本 B 访问 404 → 需共享存储（MinIO/NFS） |
| ② | **进程内缓存不一致** | `DictService.cache`（24h TTL，`refreshCache` 只清本实例）；`SysParamService.cache` | A 改字典，B 最长 24h 才生效 |
| ③ | **编号生成竞态** | `nextCode()` 读 `max(yearSeq)` 再 +1 | 两副本取到同号；被唯一约束挡住 → 报错需重试 |

**Redis 的用途与替代**：共享缓存→缩短 TTL+版本号；广播→Pub/Sub 或自然过期；
分布式锁→DB 唯一约束+重试 / `SELECT ... FOR UPDATE`；会话→**不需要**；限流→nginx `limit_req`。

**路径**：单实例（垂直扩容）→ 要冗余时**先修 ①②③** → 多副本成常态再引入 Redis → 最后读写分离/CDN。

**部署要点**：多副本需前置负载均衡；**不需要 session sticky**；需外置共享 PG + 共享存储。

## 6. 招标域表结构（设计 A）

### 6.1 决策

✅ **已决策：设计 A** —— 招标作为**一种采购方式**并入现有采购工作流。

**决定性证据**：现有系统已把"招标"建模为**采购方式**——`procurement_source` 字典五类之一
（招标采购/询价采购/谈判采购/直接采购/框架协议），且 `ContractExt` 已有
`procurementSrc`、`bidName`(招标名称)、`bidStartDate`(开始招标)、`bidWinDate`(定标时间)。
即：**在既有语义里，招标 ⊂ 采购，不是并列的两个域。**

### 6.2 落地增量（只加两张结构化表）

> **实施状态（2026-10-19）：✅ 已实施**（迁移 `20261019000000_tender_bidder_and_evaluation`）。
> 实际落地与下面的草图有**两处有意偏差**，以代码为准：
> ① **唯一键用 `(taskId, bidderName)`**，不是 `(taskId, supplierId, round)`——`supplierId` 可空，
>    PostgreSQL 允许多个 NULL，那样约束对「未入库单位」等于不存在；
> ② **报价两轮按列建模**（`firstPreTaxTotal/firstTax/…`），不是「(单位, 轮次) 一行」——
>    导入模板与四张派生表都固定两轮，拆轮次要再加一张报价子表才不丢 `passedFirst`，得不偿失。
> 另：`status` 由服务端在**勾选拟推荐成交候选人**时驱动为 `WON` 并写 `finalPreTaxTotal`，
> 生成合同的单位与金额取自这些行（JSON `candidates` 退化为发布快照）；
> 存量 JSON 由 `ensureBiddersFromSnapshot()` 在首次读取/生成合同时**幂等回填**，不写一次性迁移脚本。
> 详见 `CLAUDE.md` §4「招标域」与 `server/test-integration/tender-bidders.int.spec.ts`。

招标域真正要补的缺口只有 4 项：① 结构化投标/响应单位（现 JSON）② 结构化评标记录（现文本/JSON）
③ 招标立项阶段 ④ 按单位的文件归档。**前两项用两张表解决，后两项可选。**

```prisma
// 投标 / 响应单位（把 ResultReport.suppliers 从 JSON 提升为关系表）

  quoteAmount Decimal?  @db.Decimal(18, 2)

  bidFileUrl  String?   // 投标/响应文件
  remark      String?
  createdBy   String?
  createdAt   DateTime  @default(now())
  version     Int       @default(0)
  updatedAt   DateTime  @updatedAt

// 评标记录（评委打分 / 排名 / 结论）
model ProcurementEvaluation {

  taskId      String
  bidderId    String
  evaluator   String
  score       Decimal?  @db.Decimal(9, 2)
  rank        Int?
  conclusion  String?   // 推荐 / 不推荐
  comment     String?
```

- **不做**：公告、采购文件、成交报告、价格对比——已存在，直接复用。
- **兼容**：`ResultReport.suppliers/candidates` **保留为发布快照**，避免破坏已发布数据。
- **立项**：若需"招标准备/立项"这类前置环节，优先给 `ProcurementTask` 加前置状态，而非新建项目表。

### 6.3 转为"独立招标域（设计 B）"的信号

出现任一即重新评估：① 有**独立招标部门/制度**、招标生命周期独立于采购；② 公告需**对外发布**或对接
外部招标代理/交易平台；③ 招标项目与采购任务是**多对多**。

### 6.4 约定对齐（必须遵守）

主键 `cuid`；`version Int @default(0)`；`projectId` + `@index`；字典编码字符串（新增
`bidder_status` 等）；**不加数据库枚举**（沿用"仅 `ContractType` 一个 enum"）；文件落盘走
`common/services/storage.service.ts` 的 `StorageService`（`FileController` 只是上传入口）；
导出用 `ExcelService`/`ImportRunnerService`；权限码 `tender:view/edit` 注册进后端 `MENU_TREE`
与前端 `ICON_MAP`；迁移用 `npx prisma migrate dev`（**禁 `db push`**）。

## 7. 采购下游（订单 / 收货 / 对账）与现有单据的复用边界

### 7.1 核心原则：**收货 = 收领单，不再造"收货单"**

| 方案单据 | 复用对象 | 结论 |
|---|---|---|
| 收货单 / 到货验收 | **`ReceiptOrder`（已存在）** | ✅ 复用，仅加 `purchaseOrderId String?` |
| 验收数量 | `ReceiptOrderDetail.deliveryQty/receivedQty` | ✅ 已具备 |
| 结算 / 付款 | `Settlement` / `PaymentRecord` | ✅ 复用 |
| 采购订单 | 无 | 🆕 新增 `PurchaseOrder` + `PurchaseOrderItem` |
| 对账单 | 无 | 🆕 新增 `Reconciliation` |

现状确认：**无**采购订单/收货单/对账实体；`ReceiptOrder` 保存即 `pushToDailyReport()`（幂等）并自动入
`AssetLedger`；`Settlement/PaymentRecord/Invoice` 与收领单**无直接外键**，仅经 `contractId/projectId` 间接相关。

### 7.2 新增表（最小集）


### 7.3 单据贯通链

```
采购任务/招标定标 → 合同(含物资清单) → 采购订单 → 收领单(到货验收) → 总日报/资产台账
采购订单/收领单 → 对账单 → 结算单 → 付款 → 核销 ↔ 发票
```

### 7.4 边界规则（防双写/口径分裂）

1. **收货只在收领单**——订单的 `receivedQty` 由收领单**汇总回写**（只读派生）。
2. **数量真相在收领单、金额真相在合同/订单、票在发票**；**对账单只是快照汇总**。
3. **对账 ≠ 结算**：对账确认账目；结算据此产生结算单并进入付款。
4. **兼容现状**：`ReceiptOrder.purchaseOrderId` **可空**，现有流程不受影响。
5. **可退化**：若企业不按订单管理，可去掉 `PurchaseOrder`，让收领单直接关联合同 + 直接对账。

## 8. 进出场（决策：只做物资）

### 8.1 决策

✅ **已决策：只做物资进出场**（2026-10-13）。**不建任何新表、不做人员/车辆。**

### 8.2 依据：物资进出场已大部建模

- **`AssetLedger` 已建模进出场**：`sourceCode`（采购/调入/调出/处置…）、`qty`(**进/出场数量**)、
  `price`(进/出场单价)、`transferOutPrice`、`turnoverCount` + 在用/闲置/报废/丢失四态。
- **`DailyReport` 已有**：`entryDate`(进场日期)、`plateNo`(车牌号)、`receiver`、`receiveUnit`、`laborContract`。
- **`ReceiptOrder`** = 物资进场登记（送货/实收）+ 推送日报 + 自动入资产台账。

### 8.3 结论

- 复用 `AssetLedger` / `DailyReport` / `ReceiptOrder`；**几乎零改动**，可选补 `DailyReport.exitDate`(出场日期)。
- 原方案的 `access_record` / `access_approval` 表、门禁/人脸/RFID、扫码凭证**均不做**。
- （若将来确需**人员/车辆**进出场，建议破例建一张 `AccessRecord` 轻量表 + "凭单进出"，
  而非硬塞进收领单/日报——与物资单据语义冲突。）

## 9. 数据权限与敏感字段

**现状（2026-10-14 更新）**：功能级 RBAC（34 个 `module:view/edit` 码）；**行级数据权限、字段级加密 0 命中**；
**日志脱敏已完成**（`common/utils/mask.ts` 白名单：凭据 / 银行账号 / 证件号 / 联系方式，
拦截器对 params 与变更前后快照深度打码；历史明文由迁移 `20261016000000_scrub_log_secrets` 清洗）；
**响应体按角色打码（展示脱敏）尚未做**——需先定"哪些角色看不到哪些字段"。

| 层级 | 做法 | 成本 | 建议 |
|---|---|---|---|
| ① 展示脱敏 | 序列化打码（`****1234`），按权限决定 | 低 | ✅ 先做 |
| ② 日志脱敏白名单 | 扩展操作日志脱敏字段（现仅 password） | 低 | ✅ **已完成**（2026-10-14） |
| ③ 字段级权限 | 某些角色读不到该字段 | 中 | 🟡 按需 |
| ④ 加密存储 | AES / `pgcrypto` + 密钥管理 | 高 | 🟡 仅合规硬要求 |

  ⚠️ **无部门模型**（已移除）→ `DEPT` 维度不成立。
  **触发条件**：出现"同项目内不同人可见范围不同"。

## 10. 合同履约跟踪

**现状（已有不少）**：`Contract.execStatus` 已有五态字典（草稿/未使用/**执行中**/**已完未结**/**已完已结**）；
下游数据齐备（Settlement/PaymentRecord/ReceiptOrder/Invoice/DailyReport）；`dashboard/reminders` 端点已存在；
`ArchiveLog` 是**通用数据归档**，非合同归档。

**缺口**：履约**节点/里程碑**、履约**进度**、合同**归档**、与采购订单联动。

**设计**：
- **① 派生进度（优先，零表）**：仿 `ledger.service.ts` 批量聚合，算"已收/已结/已付/开票"比例与逾期。
- **② 节点表（可选）**：`ContractFulfillment`（节点名/计划 vs 实际日期/状态/责任人）——
  仅当需要"计划节点 + 逾期 + 违约"。
- **③ 归档**：`Contract` 加 `archivedAt/archivedBy` → 校验下游完整 → **锁定**（守卫仿 `workflowGuards`）
  → 可选导出归档包。
- **④ 提醒**：复用 `NotificationService` + `dashboard/reminders`。

**边界**：**不要重复结算/付款/收货单据**——履约是它们的**汇总视角**（与台账同哲学）；
优先扩展 `execStatus` 字典，而非新增状态字段。

## 11. 供应商门户 / 外部账号体系

**现状**：纯内部系统——`User` **无 `userType`/`supplierId`**、**无注册端点**、portal/guest 0 命中。

**结论：供应商接入是全新安全边界，风险高于成本，建议放最后。**

| 角色 | 性质 | 结论 |
|---|---|---|
| 采购/现场人员 | 内部 | ✅ 现有账号即可 |
| 评标专家 | 内部/受聘 → 内部账号；**外部专家 → 新边界** | 🟡 视性质 |
| **供应商** | **外部法人主体** | ⚠️ **全新安全边界** |

**风险**：数据隔离当前是**约定（非强制）**，越权 = 看到竞对报价/别家合同 → **商业事故**。

| 选项 | 成本 | 适用 |
|---|---|---|
| A. 不做（现状，走导出/通知） | 0 | 无自助诉求 ✅ |
| B. 轻量外部账号（`userType`+`supplierId` + 强制过滤） | 中 | 需供应商在线看自己单据 |
| C. 独立门户 | 高 | 大规模强隔离 |

**若做 B，前置条件是"强制数据范围"**（与 §9 的 DataScope 同一底座）。

## 12. 低代码能力

**现状**：已有三层配置化——字典驱动、模板驱动（`{{变量}}`）、列配置（`ledger.columns.config`）、
系统参数。即**"内容与选项"层已可配**，缺的是"**结构与流程**"层。

**结论**：低代码 = 战略级投入，**当前不缺**。若确有诉求，**只做 L1 受控字段元数据 + 流程四表**，
**避免 L2+ 自由表单**——本项目"强关系、强台账、强导入导出"与低代码的"自由结构"**天然冲突**
（动态表单 → JSON/EAV → 失去类型/约束/索引，台账取数变难）。

## 14. MQ / 异步替代方案

**结论：暂不需要 MQ。** 单体+同库下，同步调用一致性**强于** MQ 最终一致。

- **现状**：跨模块联动**同步同进程**（`publish()` 直接 `await generateLinkedContract(...)`）；
  `ImportTask` 是"DB 记录 + 进程内 fire-and-forget"（2026-10-13 时**无 worker 轮询、崩溃会卡 `RUNNING`**；
  **该缺陷已于 2026-10-14 修复**，见下条）。
- **替代**：**DB 队列表 + 轮询 worker**——worker 用 PG 原生 `SELECT ... FOR UPDATE SKIP LOCKED` 领取
  → **多副本安全、无重复**；`lockedAt` 超时可重投 → **崩溃可恢复**。现成轮子：**pg-boss**（基于 PG，无需 Redis/MQ）。
  或**事务性发件箱**（事件与业务同事务写入，将来接 MQ 只换投递端）。
- **上 MQ 的触发条件**：拆微服务 / 跨系统集成 / 真削峰。
- **顺带改进 → ✅ 已做（2026-10-14）**：`ImportTask` 已补**崩溃恢复**（`execute()` 写 `lockedAt` 心跳、
  启动时与每 5 分钟 `reapStaleTasks()` 回收超 10 分钟无心跳的任务）与**幂等去重键**
  （模块+文件名+行数+内容摘要的 sha1 + PG 事务级咨询锁串行化同键提交）——
  迁移 `20261017000000_import_task_recovery`，判据在 `common/services/import-task.service.ts`，
  契约由 `server/test/importTask.spec.mts` 与 `test-integration/import-two-phase.int.spec.ts` 锁定。
  **真正的 DB 队列 worker（`FOR UPDATE SKIP LOCKED`）仍未做**——它是"上多副本"时才需要的，
  与 §4 的多副本三项前置同批考虑。

## 15. 存储选型（是否引入 MongoDB）

**结论：❌ 不需要。**

- **附件/图片是二进制大对象**，不该进文档数据库（GridFS 或 base64 都不如对象存储）。
  正确处理：**文件本体**放对象存储，**DB 只存元数据**（url + fileName + size）——
  **现有系统已是这个架构**（`file.controller.ts` 落盘，表存 URL：
  `ContractAttachment.url`、`Invoice.imageUrl`、`Subcontractor.idCardFront/Back/...`）。
- **元数据 Schema 并不"灵活"**（就是 `{fileName,url,size}`）；真正会变的**业务字段**，
  现有已用 **`String? // JSON`** 覆盖 **14 处**。要更强用 **PG 原生 `jsonb`**（当前 0 处）——
  **优于 Mongo**（同库同事务）。
- **值得做的演进**：文件本体 → **对象存储（MinIO/S3）**（落盘写入点 3 处已收敛到 `StorageService`，
  换实现即接；静态资源服务需同步改为代理/重定向）；
  半结构化字段 → **PG `jsonb`**。

## 16. 实施路径建议

相较原方案（重写 + 微服务）**工作量下降一个数量级**。建议顺序：

1. **设计**（先做）：采购域单据关系（任务→合同→订单→收货→对账→结算）+ 招标域两张表；
   明确与现有收领单/结算的复用边界。
2. **招标域**：`ProcurementBidder` + `ProcurementEvaluation` + 页面（在现有采购工作流上）。
3. **采购下游**：`PurchaseOrder`(+Item) → 到货验收（复用收领单）→ `Reconciliation`。
4. **合同增强**：履约派生进度 →（按需）`ContractFulfillment` → 归档。
5. **进出场**：复用现有，可选补 `DailyReport.exitDate`。
6. **按需后续**：通知通道适配器（企微/钉钉）、框架级响应式、pg-boss、对象存储。
