> 审计对象：`docs/AI应用落地计划.md` 中已交付的四个课题（6-9 / 3-9 / 4-9 / 7-11）。
> 方式：里程碑逐条核对 + 只读代码审计 + 最小复现脚本（`ts-node` 直调纯函数与取数函数，不连库）。

## 5. 根因

1. **夹具自证**：三个课题的夹具形状由我设计，与真实落库形状不一致（最典型 H5：价格对比表 JSON 的 `materialBaseId` 其实是总清单行 id）。`npm test` 全绿只证明「实现符合我的假设」。
2. **出口条件被替代**：`test:int`、真实数据评测、浏览器渲染三项从未执行，因此「实现 vs 真实数据」的偏差没有任何一道闸门。
3. **对账器只管命中事实，不管提示词自己给模型的数字**（M1/H7/H8）：机制本身对，允许集合取窄了，于是正常输出被判编造。
4. **「未判定」只做了一半**：数据缺口能进 `notEvaluated` 的路径对，但「停用 / 早退 / 键不匹配」三条路径都是静默通过（H3/H4/H5/M5）。

**第三批（噪音与文案）**：M1（把样本/摘要数字纳入允许集合）、M3/M4/M8/M9/M10、L1–L5。

每批完成后按仓库铁律验收：`npm test` + 两个 build + 针对每条缺陷补一个**用真实落库形状**的回归用例（夹具从「我设计」改成「按 `schema.prisma` + service 写入形状构造」）。
