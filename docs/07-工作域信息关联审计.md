## 1. 审计方法

1. 解析 `server/prisma/schema.prisma`：对每个 model 收集
   ① 形如 `xxxId` 的标量字段；② `@relation(fields: [...])` 承载的外键字段。
   **`xxxId` 不在 ② 中 = 悬空引用**（无引用完整性）。
2. 对每个悬空字段，grep `server/src` 判断是**在用**（弱关联）还是**未用**（死字段）。
3. 人工核对跨域链路的显式外键是否存在。

## 附录 · 悬空引用检测脚本

```python
# 解析 schema.prisma，列出「有 xxxId 字段但无 @relation 外键」的字段
import re
p = "server/prisma/schema.prisma"
models, cur = {}, None
for ln in open(p, encoding="utf-8").read().splitlines():
    m = re.match(r"model\s+(\w+)\s*\{", ln)
    if m:
        cur = m.group(1); models[cur] = {"fields": [], "rel": set()}; continue
    if cur and re.match(r"\}", ln):
        cur = None; continue
    if not cur: continue
    s = ln.strip()
    if not s or s.startswith(("//", "@@")): continue
    models[cur]["fields"].append(s)
    fm = re.search(r"@relation\([^)]*fields:\s*\[([^\]]*)\]", ln)
    if fm:
        models[cur]["rel"] |= {f.strip() for f in fm.group(1).split(",")}
for name, d in models.items():
    dg = [re.match(r"^(\w+)\s", s).group(1) for s in d["fields"]
          if re.match(r"^(\w+)\s+(String|Int)\??(\s|$)", s)
          and re.match(r"^(\w+)\s", s).group(1).endswith("Id")
          and re.match(r"^(\w+)\s", s).group(1) != "id"
          and re.match(r"^(\w+)\s", s).group(1) not in d["rel"]]
    if dg:
        print(f"{name}: {', '.join(sorted(set(dg)))}")
```

> 实测输出：**27 个悬空字段，涉及 15 个模型**（见 §3）。

### ① 结算台账 ↔ 结算单：要不要强关联？

| | |
|---|---|
| **现状（证据）** | `SettlementLedger` **无 `settlementId`**，只靠 `contractId + settleMonth` 聚合；台账行由 `settlement.service` 的 `computeLedgerAutoFields()` 按 `contractId + 月` **upsert 派生** |
| **🔻 关键证据** | 它是**派生表**，一行台账的数据取自**四方**：结算单、发票、保理贴息、逾期利息（`settlement.service` 的 combos 汇总段）→ 一行台账常常**不对应任何单一结算单** |
| **选项 A · 维持聚合 + 写死口径** | 成本 0。在台账页/文档写明"结算台账按**合同 + 月份**聚合，一行不代表某一张结算单" |
| **选项 B · 加 `settlementId`** | 要先把"派生"语义拆掉（改为结算单落库时同步写台账），并定义"一结算单对多台账行"的归属；与现有 upsert 逻辑冲突，改动面覆盖结算/发票/保理/逾期四处 |
| **决定的影响** | 只影响"能否从台账反查结算单"，不影响任何金额口径 |
| **不决定的后果** | 不阻塞；但业务若拿台账去对结算单会对不上号，而系统不会提示这一点 |
| **建议** | **A**（并写进口径说明）——B 的成本与收益不成比例 |

### ② 资金费用 ↔ 结算 / 付款：贴息与逾期利息要不要归属到单据？

| | |
|---|---|
| **现状（证据）** | `FactoringCost`（融资贴息）与 `OverdueInterest`（逾期利息）都只挂 `contractId`（FK）+ `settlementMonth`（**字符串** "YYYY-MM"），与具体结算单、付款记录**没有外键** |
| **选项 A · 写死"按合同 + 月份汇总"** | 成本 0。台账/统计口径保持现状（`settlementLedger` 的 `factoringDiscount`/`overdueInterest` 已经是按合同+月汇总） |
| **选项 B · 加 `settlementId` / `paymentId`** | 可回答"这笔贴息/利息归属哪张结算单、哪笔付款"；代价：逾期引擎的取数（`overdue-calculator` + `overdue-summary` 的汇总口径）要跟着改，且存量数据无归属、需回填策略 |
| **决定的影响** | 影响"费用能否归到单据"；B 会改动**已收敛过的**汇总口径（`overdue-summary.ts` 那条单一实现），风险中等 |
| **不决定的后果** | 不阻塞；但"这笔贴息是谁的"只能靠月份人工对应 |
| **建议** | **A**，除非财务明确要按单据核费用 |

### ③ 收领单 ↔ 结算 / 付款 / 发票：要不要显式关联？

| | |
|---|---|
| **现状（证据）** | 三者之间只经 `contractId` / `projectId` **间接**表达：`ReceiptOrder.materialContractId` 指到合同，但结算/付款/发票上没有 `receiptOrderId` |
| **选项 A · 写死"只按合同聚合"** | 成本 0。文档写明"收领单与结算/付款/发票之间靠合同关联，不逐单对应" |
| **选项 B · 补 FK 或关联表** | 可回答"这笔结算对应哪些收领单"；代价：收领单可能对应多张结算单、且推送到日报后数量已被合并，归属规则需要业务定义（不是加个列就完事） |
| **决定的影响** | 影响"数量链条能否逐单追溯"；与 §2.2 A（现场确认）的闸门是两件事，别混 |
| **不决定的后果** | 不阻塞；但"这批货对应哪次结算"只能靠合同+月份粗看 |
| **建议** | **A**（除非业务要按收领单对账） |
